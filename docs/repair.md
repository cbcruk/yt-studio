# 자동 수정 루프 — 언제 멈출 것인가

`src/core/repair.js` 를 만들고 나서 `MAX_ROUNDS` 를 3에서 얼마로 조절할지
따져 본 메모다. 결론부터: **그 상수는 조절할 손잡이가 아니었다.** 루프를
실제로 멈추는 건 다른 줄이고, 거기서부터 기준을 다시 세웠다.

무엇을 만드는 도구인지는 [README](../README.md#검증기가-잡은-것은-사람-대신-되묻는다) 에 있다.

---

## 숫자는 이미 안 쓰이는 손잡이다

멈추는 조건이 둘인데, 둘 중 더 빡빡한 쪽이 항상 먼저 걸린다.

```js
if (prev && !prev.lost && errors.length >= prev.errors.length) break;
```

라운드 3에 가려면 오류가 **매 라운드 엄격히 줄어야** 한다. 그래서:

| | 3번을 다 쓰려면 | 4번째 라운드가 생기려면 |
|---|---|---|
| 첫 답의 오류 개수 | 2개 이상 | 3개 이상 (매번 정확히 하나씩만 고쳐 가면서) |

첫 답에 오류가 셋인데 모델이 한 번에 하나씩만 고치는 상황은 흔하지 않다.
`MAX_ROUNDS` 를 4나 5로 올려도 호출이 거의 안 늘고, 3으로 둬도 거의 안 잘린다.
**조절할 것은 저 상수가 아니라 위 비교식이다.**

## 뭉쳐 있던 질문 셋

`MAX_ROUNDS` 하나에 서로 다른 질문 셋이 들어가 있다.

### (a) 또 부를 가치가 있나 — 진전의 정의

지금은 오류 **개수**로 잰다. 두 군데서 틀린다.

- **멈추면 안 되는데 멈춤.** 후보를 셋 줬는데 모델이 그중 틀린 걸 골랐다 →
  개수는 1 → 1, 오류는 다른 것. 진전이 있었는데 정지한다.
- **멈춰야 하는데 계속.** 모델이 오류 난 옵션을 고치는 대신 **지워서** 개수가
  0이 된다. 검증기는 초록이고 사용자 요구는 사라졌다. 라운드 캡은 여기에 아무
  역할도 못 한다.

개수가 아니라 **오류의 신원(집합)** 으로 재야 한다. 직전 오류가 하나라도
없어졌으면 진전, 이미 본 적 있는 집합이 다시 나오면 순환이므로 정지 —
A→B→A 진동까지 잡힌다.

`best` 를 고를 때 동점이면 먼저 것이 이기는 지금 규칙은 그대로 둔다. 이른
라운드일수록 원래 요구에서 덜 표류했다.

### (b) 이 오류가 되물어서 고쳐지는 종류인가

`lint.js` 가 내는 오류를 이 기준으로 가르면 선이 꽤 선명하다.

| 우리가 답까지 알려 준 것 | 틀렸다고만 말한 것 |
|---|---|
| `no-flag` + 후보 3개 | `-f` · `-o` 파서 메시지 (`7번째 글자 근처`) |
| `choices` 목록 | **후보가 하나도 없는 `no-flag`** |
| `no-value` + metavar | |
| URL 없음 | |

왼쪽은 되물으면 거의 한 번에 붙는다 — 정답을 프롬프트에 실어 보내는 셈이다.
여기라면 라운드를 더 줘도 아깝지 않다.

오른쪽 아래 칸이 중요하다. `--bogus-flag` 처럼 **가까운 후보조차 없다는 건
yt-dlp 에 그 기능이 없다**는 뜻이다. 모델이 능력을 지어낸 것이므로 몇 번을
되물어도 다른 걸 또 지어낸다. 옳은 동작은 라운드를 늘리는 게 아니라 **1번에
끊고 "yt-dlp 에 그런 기능이 없다"고 말하는 것**이다. 세 번 헛돈 뒤에 같은
결론을 내는 것보다 그게 더 나은 답이다.

### (c) 얼마나 기다리게 할 수 있나 — 돈이 아니라 지연이다

라운드 하나는 캐시된 6천 토큰 접두어 + 짧은 출력이라 돈은 사실상 무시할 만하다.
진짜 비용은 **화면이 안 변한 채 늘어나는 대기**다. 그런데 이건 숫자로 풀
문제가 아니라 UI 로 풀 문제다 — 2라운드에 들어갈 때 1라운드 명령어와 검증기가
뭘 잡았는지를 먼저 보여 주면, 기다림이 "멈춘 것"이 아니라 "고치는 중"으로 읽힌다.

## 캡의 성격

3번에서 멈춰도 사용자는 **고치기 버튼을 한 번 더 누를 수 있다.** 그러면 부분적으로
고쳐진 명령어에서 루프가 새로 시작한다. 실효 상한은 이미 무한이고,
`MAX_ROUNDS` 는 포기하는 지점이 아니라 **사람에게 허락을 다시 받는 지점**이다.

그렇게 보면 기준이 뒤집힌다. "몇 번이면 고쳐지나"가 아니라 **"사람이 버튼만 보고
얼마나 기다릴 수 있나"** 이고, 답은 작은 수다. 3은 올릴 대상이 아니라 이미 천장에
가깝다. 2도 방어할 수 있다.

## 할 일 — 이 순서로

지금은 데이터가 없다. 어떤 숫자를 대도 포장한 추측이다.

1. **숫자는 건드리지 않는다** — 거의 안 걸린다.
2. `errors.length` 비교를 **오류 신원 집합 + 순환 감지**로 바꾼다.
   실제 정지 규칙은 여기다.
3. **후보 없는 unknown flag 는 1번에 끊는다** — 되물어서 고쳐지는 종류가 아니다.
4. `trace` 를 기록한다. 이미 계산해 놓고 버리고 있다 — 라운드 수 · 첫 오류
   개수 · 오류 종류 · 수렴 여부. localStorage 로 되고, 한두 주 쓰면 숫자가
   스스로 정해진다.
5. 그때 데이터가 시키면 캡을 상수 대신 **남은 오류의 종류로** 정한다 — 답까지
   알려 준 오류만 남았으면 한 번 더, 아니면 멈춤.

2·3은 지금 바로 짤 수 있고 단위 테스트도 대본으로 다 덮인다.
